## 自动测试复现

解压源码 ZIP，进入项目目录：

```powershell
npm ci --ignore-scripts
npm test
npm run demo
npm run build
```

`tests/*.test.cjs` 使用 Node 内置测试器。`xmldom` 和 `fflate` 的开发依赖固定在锁文件中，正式 XPI 自带所需的 fflate。安装成品不需要运行这些命令。

测试包含内容控件保护的回归用例：先确认块级内容控件内的 `[1]` 会被错误允许，再修正并确认其不能转换，且不能作为参考文献表标记位置。其他重要断言包括：未选中位置不转换、原图片解压字节保留、同簇同文献去重、引用出现标识唯一、旧 Zotero 文档不能二次转换。

## 隔离宿主测试复现

此项供开发者回归使用，不能指向个人日常资料目录。先在项目同级目录放置专用 Zotero 运行时副本，例如 `runtime7/Zotero_win-x64/`。从官方下载的发行包提取；不要把测试入口写入正式安装目录。

```powershell
python scripts/prepare-runtime.py acceptance7 --word-test
python scripts/instrument-runtime.py ../runtime7/Zotero_win-x64
```

`prepare-runtime.py` 在项目同级创建 `test-acceptance7/`，包含全新 profile、data、两个 XPI 和配置。`instrument-runtime.py` 对目标路径有工作目录限制，修改副本的 `app/omni.ja`，让宿主启动后用 AddonManager 安装这两个 XPI。需要重新测试时更换测试名称，避免旧输出文件导致“拒绝覆盖”。

启动副本时，明确传入 `-no-remote -profile <测试 profile 的绝对路径> -purgecaches -ZoteroDebugText`。为该进程设置专用 TEMP、TMP；不同大版本应顺序运行，避免宿主解压样式时相互影响。Windows 后台启动可用 `Start-Process`，指定 `-WindowStyle Hidden`，不要让它使用日常 Zotero profile。

观察测试目录的 `result.json`：应为 `ok: true`，含 44 项检查。同目录额外生成 `converted-ui.docx`，用于验证设置菜单选择的样式和语言实际用于按钮导出流程。若启用 `--word-test`，保留该测试 Zotero 进程，用桌面 Word 打开同目录的 `converted.docx`，再创建 `word-ready.json`（内容 `{}`）。脚本会核对合成文档四个唯一引用标识，再执行官方刷新，修改测试库中的合成条目并再次刷新。`word-result.json` 应为 `ok: true` 且包含 5 项检查。

Word 首次 Refresh 会重新分配 Zotero 的文档 sessionID，因此测试用每处引用的唯一 citationID 核对目标文档，而不是要求 sessionID 恒定。不匹配则拒绝执行后续修改。完成后保存并关闭合成 Word 文档，只结束对应测试 profile 的进程。

## 失败与限制验收

还应使用副本分别试验：含现有 Zotero 引用、开启修订、未接受修订、已有旧手写参考文献表、超过大小限制的文件，应明确拒绝。超链接、普通域、内容控件中的候选应显示受保护；页眉页脚、脚注尾注、批注不转换。检查图片、表格、节和非引用文字的保留情况。

真实论文可能有上述合成样例未覆盖的 OOXML 结构。首次使用时，对照原件逐页检查布局和引用，确认后再继续编辑。第一版不自动识别旧参考文献内容、不处理脚注型样式，也不合并已有 Zotero 引用。

WPS 单独验收应区分三个环节：扫描 WPS 保存的普通 DOCX；用 Word 刷新生成结果；WPS 重新保存后再回到 Word 检查域是否仍可编辑。当前没有执行这组测试，不能把其中任一步的成功推导为 WPS 原生 Zotero 支持。
